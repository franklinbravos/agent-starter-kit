# Techniques — Tested Recipes

Reusable, read-only-first techniques confirmed to work during real engagements. Each entry states the goal, the command, and how to read the result.

## Passive reconnaissance

- **Enumerate subdomains via Certificate Transparency.** `crt.sh` and Cert Spotter cross-check each other; either may be rate-limited or flaky.
  - `curl -s "https://crt.sh/?q=%25.<domain>&output=json"` — parse `name_value`.
  - `curl -s "https://api.certspotter.com/v1/issuances?domain=<domain>&include_subdomains=true&expand=dns_names"`
- **Discover correlated domains by certificate organization.** `curl -s "https://crt.sh/?O=<ORG>&output=json"` returns certificates whose subject organization matches; parse `.common_name` for the domains. This surfaces sibling domains that share no brand string (sibling domains of the group). Confirm each with WHOIS registrant/CNPJ and a shared MX before any request.
- **DNS and mail posture.** `dig +short NS/MX/TXT/AAAA/CAA <domain>` and `dig +short TXT _dmarc.<domain>`. A DMARC `p=none` permits spoofing; `p=reject` enforces.
- **Attribute a new subdomain before rating it.** `dig +short -x <ip>` and `whois <ip>` classify the host: a PTR under the target's own name (self-hosted) differs from a PTR at a vendor (`*.exacttarget.com`, `*.amazonaws.com`) or a third-party netblock (`whois <ip> | grep -iE 'owner|orgname|descr'`). A name that resolves to a vendor edge is OSINT-only for the vendor's part, and its exposure is an inventory item, not a client-server finding. This separates "new asset" from "new vendor relationship" without touching the vendor.
- **TLS fingerprint.** `echo | openssl s_client -connect <host>:443 -servername <host> 2>/dev/null | openssl x509 -noout -subject -issuer -dates`.
- **HTTP fingerprint.** `curl -sS -D - -o /dev/null https://<host>/` — server, CDN, security headers, cookie flags, redirect chain, framework hints (`x-redirect-by`, `x-magento-*`, `x-powered-by`, `X-Jenkins`).
- **Mine `robots.txt` for hostnames CT misses.** `GET /robots.txt` on the storefront and read the `Disallow` entries as a source of internal names. Resolve each leaked name (`dig +short`) against two public resolvers; a name that resolves to the client's own IP block is live internal surface the Certificate Transparency did not list. Confirm block ownership with WHOIS/RDAP and the SPF `ip4:` statement before treating it as in-scope.

- **Distinguish GoDaddy Managed WordPress from a standalone Cloudflare proxy.** A host behind GoDaddy's
  managed-WP edge returns `server: cloudflare` + `cf-ray` **and** `x-gateway-cache-*`/`x-gateway-request-id`
  headers, with a GoDaddy DV certificate and rDNS `*.secureserver.net`. Do not read this as a user-provisioned
  Cloudflare WAF; the origin is GoDaddy itself.
- **Confirm wildcard DNS before counting subdomains.** `dig +short A <random-label>.<domain>` — if a random label resolves, the zone answers with a wildcard and every candidate looks alive. A wildcard makes resolved names useless as an inventory; only names observed in an independent source count. A negative probe (random label does not resolve) turns each resolved candidate into a real DNS record.
- **Read per-tenant certificate names as a business signal.** A SaaS that issues one certificate per tenant (`<customer>.workspaces.<domain>`, `fws-<customer>.<domain>`) publishes its customer list in Certificate Transparency. Record the internal naming and the tenant names, and rate it as a confidentiality observation — it is inherent to CT, not a technical vulnerability. A wildcard certificate for the tenant label removes the disclosure.

## Version discovery

- **Magento version via setup page.** `GET /setup/` often exposes `Magento Version X.Y.Z-pN`.
- **Jenkins version via header.** `X-Jenkins: <version>` on any response, including `403`.
- **GitLab version via page data.** The `gon` JSON on `/help` or the sign-in page carries `gitlab_version` `{major, minor, patch}`.
- **WordPress hardening probe.** `GET /wp-json/wp/v2/users` (401/403 = hardened), `/xmlrpc.php` (403 = hardened), `/wp-login.php` (404 = hidden).
- **WordPress registration/access sweep (read-only).** In one bounded pass: `GET /wp-login.php?action=register` (302 `registration=disabled` = off), `GET /wp-login.php?action=lostpassword`, `GET /wp-sitemap-users-1.xml` (author enumeration), `GET /wp-json/` (route/namespace inventory), `GET /wp-json/wp/v2/users/1/application-passwords` (501 = disabled), and `GET` the config/backup set (`/wp-config.php.bak`, `/.env`, `/.git/config`, `/wp-content/debug.log`). Then `POST` **only** bodies that cannot create state: `POST /wp-json/wp/v2/users` with `{}` → 400 (missing params) and with a full body → 401 (`rest_cannot_create_user`); `POST /wp-json/wp/v2/comments {}` → 401 (`rest_comment_login_required`). This proves the creation boundary without creating anything.
- **Rails/Devise portal registration probe.** `GET /users/sign_up` — a `404` with the platform's own 404 template proves self-registration is disabled; a `200` form proves it is open. `GET /users/password/new` confirms the reset route. Read-only; do not create an account or submit credentials on a vendor-hosted tenant without separate authorization.
- **Version the WordPress plugin stack from `?ver=` on a rendered page.** Fetch a published page (from `GET /wp-json/wp/v2/pages?status=publish`) and grep `?ver=` per plugin path — core (`wp-includes`), Elementor (`frontend.min.css`), Elementor Pro (`webpack-pro.runtime.min.js`), Essential Addons (`general.min.js`). Cross-check each against the watchlist range before attributing a CVE; a hashed `?ver=` (e.g. a content hash) means the version is not observable and no CVE may be attributed.
- **Tomcat version via a forced 404.** Request a non-existent path; the default error page embeds `<h3>Apache Tomcat/X.Y.Z</h3>` even when the connector only advertises `Server: Apache-Coyote/1.1`. One probe turns a versionless banner into an exact (often EOL) version.
- **Tomcat management-app reachability.** `GET /manager/html` and `/host-manager/html`; a `401` with `WWW-Authenticate: Basic realm="Tomcat Manager Application"` means the console is protected, a `200` means it is exposed. `/examples/` returning `200` means the sample webapp is deployed.
- **SoftExpert version via the login page.** The login `<title>` carries `SoftExpert Suite X.Y` and asset paths embed the build (`/se/v89986/…`). `GET /softexpert/version` may `403` — the title and asset paths are the oracle, not that endpoint.
- **WordPress core version via login-page assets.** `GET /wp-login.php`; the stylesheet URLs carry `?ver=X.Y.Z` for the core, and `meta generator` may name bundled plugins (e.g. Site Kit). Read the `?ver=`, not the plugin banner.
- **nginx origin version via an application error page.** With `server_tokens on`, nginx stamps its version on any error page — including a `502` returned for an application path (e.g. `/xmlrpc.php` → `502 … <center>nginx/1.27.3</center>`). Read the error page on a **subpath**, not only the root banner: it can be the only place the origin version appears, and it ties the same origin to another virtual host.
- **Grafana version via the unauthenticated `/api/health`.** `GET /api/health` returns `{"version":"X.Y.Z","commit":"…","database":"ok"}` with no auth — the login page title is only `Grafana`. Confirm the authorization boundary in the same breath: `/api/search`, `/api/user`, `/api/org` and `/api/frontend/settings` returning `401 {"message":"Unauthorized"}` proves anonymous access is disabled (a control, not a finding). Then check `/api/health`'s version against the exact NVD range before naming any CVE.

## Attack-surface probes (read-only)

- **Exposed setup / docs / APIs.** Probe `/setup/`, `/graphql`, `/rest/V1/`, `/api/documentation`, `/docs`, `/.env`, `/.git/config`, `/app/etc/env.php`, `/*.sql`, backup paths. Record status and headers.
- **GraphQL introspection.** `POST /graphql` with `{"query":"{__schema{queryType{name}}}"}` — a JSON `data.__schema` response means introspection is enabled (aids attackers; the interim mitigation for template/GraphQL flaws is not applied).
- **Open registration (do not create an account).** `GET /users/sign_up` — a rendered form with fields is evidence of a public form; whether it yields access requires an authorized test.
- **Fingerprint remote-access gateways without a version.** A Check Point Mobile Access / Remote Access VPN returns `Server: CPWS` (Check Point Web Server), a body carrying "Check Point Mobile" and the Check Point copyright, and redirects `/sslvpn/Login/Login`; a FortiGate SSL-VPN serves `/remote/login`; a Citrix NetScaler returns `NSC_*`/`NSC_USER`/`CtxsAuthId` cookies and redirects `/vpn/index.html`; all may omit the firmware version. Record the product and the exposure, label the version unknown, and name the authenticated read (console/banner) that would confirm it — never attribute a CVE from the product name alone, and never read `CPWS` as FortiGate.
- **Cookie flags.** `Set-Cookie` attributes: `Secure`, `HttpOnly`, `SameSite`. Absence of `Secure`/`HttpOnly` on a session cookie is a finding.
- **Leak the origin through the app's own redirect.** A reverse proxy misconfigured to **redirect** (not proxy) an internal path hands out the backend hostname. Request server-side routes without following redirects (`curl -sS -D - -o /dev/null https://<host>/api/`); a `301`/`302` whose `Location` is an internal name (`*.elb.amazonaws.com`, a private IP, an `http://` URL) discloses the origin. Then: `dig` it, confirm reachability with **one** read-only `GET`/`HEAD`, and check `443` (a refused 443 with a `200` on port 80 = CDN/WAF bypass over plaintext). Probe the leaked origin's sensitive paths (`/api`, `/admin`, `/server/*`) **before** rating severity — if they `404` on the origin, the impact is limited to public content.

## Supply-chain OSINT

- Extract vendor hosts from page source (`src`/`href`), answer headers, and DNS; identify platform, payments, marketing, CDN, hosting.
- For each vendor, map platform/version and check the watchlist + vendor advisories. Third parties are OSINT-only.

## Supabase-backed single-page apps

- **Find the backend.** Grep the JS bundle for `*.supabase.co`, `createClient`, and key patterns. A `sb_publishable_…` (or legacy `eyJ…` anon) key is public by design — the risk is RLS, not the key. A `sb_secret_…` key in a bundle is a critical finding.
- **Check the auth policy.** `GET /auth/v1/settings` with the public key shows `disable_signup`, `mailer_autoconfirm`, and enabled providers.
- **Measure RLS without reading rows.** `HEAD /rest/v1/<table>?select=id&limit=1` with `Prefer: count=exact`; the `content-range` header reveals whether the public key can read. `*/0` = RLS blocks anonymous; `0-N/N` with N>0 = exposed.
- **REST schema root.** `GET /rest/v1/` may return `401 {"message":"Secret API key required"}` (new Supabase behavior) — that is hardening, not a finding.
- **Edge functions.** Live at `<project>.supabase.co/functions/v1/<name>`, not on the app domain. Probe with `OPTIONS`/`GET`; an unauthenticated `GET` returning `401` confirms auth is enforced.
- **Extract tables/RPCs from the bundle.** Grep for `` .from(`table`) ``, `.select(`, `.rpc(` — this reveals the real data model to target with the RLS check.
- **Find storage buckets and test them unauthenticated.** Grep for `.storage.from(` to get bucket names, then `POST /storage/v1/object/list/<bucket>` and the `/storage/v1/object/public/<bucket>/<file>` URL with no auth — a public bucket lists and downloads.
- **Test tenant isolation via a writable tenant column.** If `profiles.organization_id` (or similar) is user-writable, read the target tenant id from a readable table (`projects.organization_id`), PATCH it onto your own row, and re-count the tenant-scoped table. Revert afterward.
- **Re-establish a Supabase session by password recovery without touching the password.** `POST /auth/v1/recover` sends a reset mail; read the message from a public inbox (`https://www.mailinator.com/api/v2/domains/public/inboxes/<inbox>`, then `/messages/<id>`), extract the `/auth/v1/verify?token=<hash>&type=recovery` link, and `GET` it: a `303` `Location` carries `#access_token=…&refresh_token=…`. Use the token directly; do not `PUT /auth/v1/user` or submit a guessed password.
- **Test the bucket the app actually uses, not the one you guess.** Grep the bundle for `storage.from(` (literal or a variable like `` gN=`<bucket-name>` ``) and for per-tenant upload path prefixes. A private `attachments` bucket can hide a second, differently-scoped bucket that the tenant hop opens.
- **Prove a storage write path without a persistent URL.** `POST /storage/v1/object/list/<bucket>` with `{"prefix":"","limit":1000}` enumerates folders; `POST /storage/v1/object/sign/<bucket>/<path>` with `{"expiresIn":60}` returns a `signedURL`; a ranged/`HEAD` `GET` of it confirms content type and size with minimal transfer.

## Next.js applications

- **Map the auth model.** A `307`/`302` to `/login` on every route means middleware auth. NextAuth exposes `/api/auth/providers`, `/api/auth/csrf`, `/api/auth/session` publicly — `/api/auth/signin/<provider>` returning `?error=Configuration` means the provider is misconfigured (no client id/secret).
- **Test the middleware bypass (CVE-2025-29927).** Add `x-middleware-subrequest` header (`middleware`, `middleware:middleware:middleware:middleware:middleware`, `pages/middleware`, `src/middleware`) to a protected route; a `200` instead of the redirect is a bypass. A repeated `307` means it is not applicable.
- **Server Actions.** Grep the bundle for `createServerReference("<id>",…,"<name>Action")` to get action IDs. Actions are invoked with `POST <page>` + `Next-Action: <id>`; a foreign `Origin` should be rejected — verify CSRF handling.
- **A white-label app's data backend can be a third party behind an in-scope token mint.** Grep the chunks for a `goFetch`/`go-token` pair: the client calls an in-scope route (e.g. `GET /api/auth/go-token?tenantId=…`) that returns a short-lived Bearer, then sends it to an external API (`https://api.<vendor>.tld…`). The mint route is in scope; the target backend is not. Decode the returned JWT locally (`aud`, `iss`, `role`, `exp − iat`) to learn the pivot scope and TTL without ever calling the third party. Test the mint route's own controls: session required, arbitrary tenant denied, missing param rejected.
- **Enumerate App Router API routes from the per-page chunks, not only the shared bundles.** The registration/login chunks carry the public routes; member-only endpoints (`profile`, `user-event`, `recently-watched`, upload) live in the chunks a given authenticated page references. Read the page's `src="/_next/static/…chunks/*.js"` list, fetch each chunk once, and grep for `"/api/…"` literals plus `fetch(`/`axios.post(` call sites.
- **Test the object-trust question without writing.** Send an update endpoint an *intentionally invalid* body and read the ORM/validation error: it often prints the `where` clause, revealing whether the target id comes from the session (body id ignored → control present) or from the client-supplied id (BOLA). No write occurs because the body fails validation first.

## JavaScript bundles and client config

- **Extract the embedded dependency manifest from a Vite bundle.** Vite apps often inline `package.json` (a JSON object with `"name"`/`"dependencies"`). Grep for `"dependencies":{` or a known dependency (`react-router`, `axios`); the surrounding object gives exact semver ranges for advisory correlation. A CRA bundle usually has none.
- **Detect development config shipped to production.** Grep the bundle for `production:!1`, `production:false`, `localhost:`, and `redirectUri`. An Angular `environment` object with `apiUrl:"http://localhost:8080/api"` and an MSAL `redirectUri:"http://localhost:4200"` inside a production bundle is a misconfiguration finding.
- **Decode any JWT found in a bundle before rating it.** Base64url-decode the payload and read `iss`, `exp`, `client_name`, and the claims. `iss: https://authsandbox.<vendor>` with a sample merchant ("Loja Exemplo") and a past `exp` is a sandbox artifact, not a live secret — rate it as a pattern risk, not a high.
- **Confirm a bucket is private with a HEAD.** `curl -sS -I https://<bucket>.s3.amazonaws.com/` — `403` = exists and denies anonymous access; `404` = name free. HEAD carries no body, so no object keys leak.
- **Classify a Firebase web API key without touching data.** The web key is public by design. Grep the bundle for `firestore|getDatabase|firebase/auth`; if absent, only analytics/messaging is used. `GET https://identitytoolkit.googleapis.com/v1/projects?key=<key>` returning `400` shows Auth/Identity Toolkit is not enabled.
- **An SPA's client routes are not HTTP-verifiable.** Every path returns the same shell (200); read route existence from the bundle, not per-route status. Probe the backend route (not the SPA) with `OPTIONS`/`HEAD`: `401` = exists and requires auth, `404` on HEAD = POST-only route.
- **Read session-token storage from the bundle.** Grep for `document.cookie` set calls and `localStorage.setItem`. A cookie set from JS has no `HttpOnly`; note `SameSite`/`Secure` and whether the token is copied into an `Authorization` header.

## Public object storage (Cloud Storage / S3)

- **Detect an anonymously listable bucket from its host header.** A CDN subdomain that answers `GET /` with `server: UploadServer` and an XML `ListBucketResult` body is a Google Cloud Storage bucket with public listing. The `<Name>` element gives the bucket name; `<IsTruncated>true</IsTruncated>` means more objects exist (paginate with `Marker`/`NextMarker` only if authorized — one page proves the misconfiguration).
- **Triage the exposure before rating it.** Read the returned XML only (no object download). Public marketing assets (`banners/`, `email/`, `*.pdf` training) make the finding about *enumeration*, not data loss — rate moderate, not high. Namespaces named `int-`, `-dev`, `staging` raise it: listing is never needed for CDN operation.
- **The bucket name outlives the hostname.** Note the bucket name from `<Name>` — the same bucket can later be referenced by a different hostname, and the fix (remove `allUsers` from bucket IAM) is per bucket, not per host.
- **An expired TLS cert does not block GCS access.** When a `dev.cdn`-style host fails validation, `curl -k` (one request) still reveals whether the bucket is public.

## Azure Blob storage

- **Detect anonymous container listing.** `GET https://<account>.blob.core.windows.net/<container>?restype=container&comp=list` with header `x-ms-version: 2021-08-06`. A `200` with `EnumerationResults` XML is public listing; `<NextMarker>` means more pages (one page proves the misconfiguration). Without the version header, Azure defaults to API version `2009-09-19` and returns `409 FeatureVersionMismatch` even for a public container — **send the header before concluding "private".**
- **Account-level listing is separate.** `GET https://<account>.blob.core.windows.net/?comp=list` returns `401` unless the account key is used — a `401` there does **not** mean the containers are private.
- **Prove anonymous object read with one GET.** Fetch a blob named in the listing (`curl -o /dev/null -w '%{http_code}'`) — a `200` confirms read. Do not download documents; the listing plus one object request is enough.
- **Triage by name, not by volume.** Count extensions (`.pdf` contracts/terms, `.zip`, `.docx`, `.psd`) to set severity; a production/CMS namespace with contracts is `médio`, not `alto`, when no secret/PII appears in names and content is not downloaded.
- **A storage account named after the app's business unit is still the client's asset.** A container referenced from an in-scope app (e.g. a `<app>-prd` CMS/portal account) is read-only in scope even when hosted by a third-party cloud; only the provider's own systems are OSINT-only.

## Historical artifacts and code indexes

- **Wayback CDX for sensitive file extensions.** `curl "http://web.archive.org/cdx/search/cdx?url=<domain>&matchType=domain&output=json&fl=original,timestamp,statuscode,mimetype&collapse=urlkey&filter=statuscode:200&filter=original:.*\.(pdf|xls|xlsx|csv|sql|zip|bak|env|json|xml)$&limit=800"` — list names only, never fetch the content. A live check of the handful that matter (`curl -w '%{http_code}'`) separates history from exposure.
- **grep.app code index is not always reachable** — `https://grep.app/api/search?q=<domain>` can return an empty body; fall back to general web search and cite the reference, never the leaked data.

## Legacy TLS on modern OpenSSL

- **`openssl s_client -tls1` fails with `no protocols available` on OpenSSL 3.x.** TLS 1.0/1.1 are disabled at the default security level. Force them with `-cipher 'DEFAULT@SECLEVEL=0'`.
- **Do NOT read `Protocol: TLSv1.1` as success.** On a rejected handshake, `s_client` still prints the *requested* protocol. A legacy protocol is accepted only when the output contains `SSL-Session:` **and** no `alert protocol version`. Grepping for `Protocol:` alone produces false positives on every host.
- **macOS has no `timeout`.** Use a plain pipe (`echo | openssl s_client …`) or `gtimeout`; a missing `timeout` makes the probe return empty and silently reports "no TLS".
- **Prove legacy-protocol acceptance with `SSL-Session`, and bound the probe without a Perl wrapper.** `echo | openssl s_client -connect <host>:443 -servername <host> -tls1 -cipher 'DEFAULT@SECLEVEL=0'`; the protocol is accepted only when the output carries `SSL-Session:` and **no** `alert protocol version`. Do **not** wrap the probe in `perl -e 'alarm shift; exec @ARGV' 20 openssl …` — it breaks `s_client`'s stdin and returns empty output that reads as "no TLS". On macOS, bound the probe with a background job plus a `sleep`+`kill` guard writing to a temp file.

## Certificate and redirect hygiene

- **A wildcard cert whose CN belongs to a different domain is a delegation signal.** `CN=*.agency-domain` with SAN including the target's wildcard (`*.target.tld`) means the target's wildcard is issued inside a third party's ACM/CA account. Report it as an ownership/dependency observation, not a vulnerability.
- **Read SANs for internal naming.** A public cert often carries `*.int.gcp.<corp>`, `*.gke2.ope.<corp>`, or an internal IdP host — inventory the internal naming printed on public certificates.
- **`X-Frame-Options: ALLOW-FROM <uri>` is dead.** Modern browsers ignore it (no clickjacking protection). Report it as a finding, separate from the host's CSP.
- **An empty CSP directive protects nothing.** `frame-ancestors;` (no value) is invalid and ignored. An empty directive is a fix, not a control.

## Database functions and RPCs

- **Test RPC authorization with a non-existent UUID, never a real record.** Call the function with the correct argument names (read them from the bundle call site, e.g. `<rpc_name>({<arg_name>})`). A `23503` foreign-key error is positive proof the function **passed the authorization check and reached the write**; a `42501`/`P0001` authorization error means a role check exists. The random id guarantees no row is created.
- **Read the parameter names from the bundle.** Grep `` .rpc(`name`,{ `` to see the exact named parameters, or PostgREST returns `PGRST202` for the wrong signature.

- **Test a Next.js source map with the chunk the page actually loads.** Grep the rendered HTML for `/_next/static/…\.js`, then request that exact URL plus `.map`. A `404` is the proof of non-exposure; guessing `/_next/static/chunks/*.js.map` returns the SPA shell (`200 text/html`) and reads as a false negative. The same rule applies to any hashed asset path — read the reference from the page, do not guess it.
- **Surface decommissioned subdomains via Wayback CDX.** `curl "http://web.archive.org/cdx/search/cdx?url=<domain>&matchType=domain&output=json&fl=original&collapse=urlkey&limit=5000"` and collect the host part of every URL. This reveals hostnames that CT/DNS brute-force miss because they no longer resolve (NXDOMAIN) — e.g. a legacy HR portal that was once public. Then `dig` each to confirm current NXDOMAIN and, if reachable, treat it as an in-scope asset.
- **Rails/Webpacker source maps via the manifest.** `GET /packs/manifest.json` lists the compiled bundles *and* their `.js.map` files. If a `.map` is served, download it and grep the `sourcesContent` for secrets and internal hostnames. Presence of the map is a finding (source exposure); absence of secrets does not remove the finding — verify both before rating.

## Authorized active testing (open registration)

- **Confirm open registration with one signup request.** When the RoE authorizes exactly one test account, send a single `POST` to the signup route with a synthetic identity (test mailbox you control + CPF with valid check digits, clearly marked as test). A `201`/`200` returning the created resource — especially a server-assigned `role`/`is_active` — confirms open provisioning. A `409`/"already exists"/message naming an address you do not control means abort, do not retry.
- **Read the confirmation gate without the OTP.** One `POST` to the login route right after signup distinguishes the gate: a `4xx` "not confirmed"/`UserNotConfirmedException` means the only barrier is the inbox; a `200` with tokens means the account is immediately usable. Never resend the code or guess it — if the test mailbox is unreadable, stop and ask for the code to be relayed.
- **Revertable evidence, no secrets in the workspace.** Keep the test password in a temp file outside the repo. Store only the identifiers needed to delete the account (internal id, provider id, e-mail, synthetic CPF) plus the exact creating request. Never copy session tokens into the workspace.
- **A timestamp labeled `Z` is not proof of UTC — compare it to the transport clock.** Body timestamps such as `created_at:…Z` can carry local time. Cross-check against the response `date:` header (GMT). A fixed offset (e.g. 3 h) is a timezone-serialization finding.
- **Read a Cognito access token's claims to map the IdP.** Base64url-decode the middle JWT segment: `iss` yields the **User Pool ID** (`…amazonaws.com/<region>_<pool>`), `client_id` the app client, `token_use`, `scope` (e.g. `aws.cognito.signin.user.admin` = the pool's self-service surface: `GetUser`, `UpdateUserAttributes`, `ChangePassword`), and `exp − iat` the TTL. The `refreshToken` is usually returned in the login JSON body, not an `HttpOnly` cookie — record the storage path, not just the token. Pool/client ids are public; the finding, if any, is the self-service surface plus a long-lived refresh token in JS-reachable storage.

- **Settle a NextAuth email provider's provisioning gate without completing sign-in.** `POST /api/auth/signin/email` (with the CSRF token from `/api/auth/csrf`) for an **unknown** address returns `302` to `/api/auth/error?error=AccessDenied`; for an **existing** account it returns `302` to `/api/auth/verify-request`. The split proves the provider is gated by an existing account and does **not** auto-provision — decided with two requests and no user created. To avoid sending mail to a stranger, use an address you control (a disposable inbox is for **receiving**, not for creating accounts) and never click the link unless the RoE authorises the account.
- **Read a registration endpoint's tenant check from its error, using an existing identity.** `POST` the signup route with the test account's own e-mail and a **syntactically valid but nonexistent** tenant id. A distinct error (`"tenant not found"`) proves the tenant is validated and reveals the validation order (tenant before duplicate check); the duplicate e-mail guarantees no second account is created. A generic error for every other malformed field shows the endpoint deliberately hides the reason — which is UX, not a vulnerability.
- **Invalid-token probes are the cheap control test for activation/reset.** `POST` the `activate`/`reset-password`/`refresh` routes with an obviously invalid token and a strong password. A uniform `4xx` in `application/problem+json` (`"link invalid"`, no ORM/stack) is the control; a raw ORM/validation error is the finding. Never send a token you did not obtain — a random value cannot collide with a real one.

## Domain-portfolio expansion (passive)

- **Reverse-IP pivot on the client's own hosts.** `curl -s "https://api.hackertarget.com/reverseiplookup/?q=<ip>"` lists hostnames that resolved to an IP. A hostname sharing the client's droplet, or a netblock owned by the domain's own technical contact, is a correlation signal for a sibling/related domain — confirm ownership through the public company registry (see next), never by probing.
- **Diff a brand-sibling domain by stack before assuming a shared tenant.** Resolve the apex and read one HTTP response: the `Server`/`X-Powered-By`/CMS markers (WordPress `link: …wp-json…`, `X-Powered-By: PHP`, LiteSpeed; Next.js/Vercel; .NET/Kestrel) plus the RDAP registrant settle whether two brand domains are one system or two. Same brand is not same infrastructure.
- **Aggregate passive subdomain sources, then resolve before use.** `curl -s "https://api.subdomain.center/?domain=<domain>"` (also HackerTarget `hostsearch`, AnubisDB, webscan, urlscan search, OTX, RapidDNS) returns many candidates; most are stale. `dig +short A` each and keep only names that resolve — the rest are historical noise.
- **Read a Brazilian domain's registrant entity.** `curl -s "https://rdap.registro.br/domain/<domain>"` returns registrant/technical/registrar handles and the entity name, plus the create/expire/last-changed dates. For a `.com` use the Verisign RDAP. This turns a brand guess into a verified owner.
- **Confirm an IP's owner from the RIR.** `whois <ip>` (LACNIC for BR ranges) prints `owner`, `ownerid` (CNPJ), `aut-num`, and the `person`/`e-mail` of the block's contact. An IP owned by the same entity as the domain's registrant/technical contact — or whose abuse contact is on the client's domain — is client infrastructure, not a third party.
- **Corroborate a sibling domain from public company data.** A group's related legal entities share CNPJ partners, address, and role e-mail. A domain hosted on the client's infrastructure **and** registered to a company in the same economic group is related infrastructure; note it, and treat a domain whose owner cannot be confirmed as OSINT-only.

## Mail and DNS hygiene sweep

- **Measure the DKIM key length, do not assume it.** Base64-decode the `p=` value and count the RSA modulus bytes: SPKI starting `MIGf` = 1024-bit, `MIIB` = 2048-bit. A `n=<bits>` tag (when present) restates it. A 1024-bit key is below current practice even when SPF/DMARC look strong.
- **Inventory the record types that are *absent*.** `dig +short DS <domain>` (empty = DNSSEC off), `TXT _mta-sts.<domain>`, `TXT _smtp._tls.<domain>`, `TXT default._bimi.<domain>`, `CAA <domain>`. Report the gaps for **every** domain in the portfolio — a hardened primary domain does not protect the siblings.
- **`_dmarc.<domain>` empty = no DMARC.** `sp=` on the primary applies only to its own subdomains, not to a separate related domain; each domain needs its own policy.
- **A CDX entry is only real if its `statuscode` is not 404.** Archived `.well-known/security.txt` or `openid-configuration` are often snapshots of 404 probes; read `fl=...,statuscode` before treating a historical path as existing.

## Public-surface route mapping (read-only)

- **Read a Next.js App Router route from the RSC payload, not the HTML.** The streamed `self.__next_f.push([1,"…"])` payload carries the router state tree (`"c":["","login"]`, `"children":[["domain",…]…]`) and the page's component names (e.g. a `RegisterForm` reference with its props). Grep the captured HTML for `children`/`__PAGE__` and for the component ids to enumerate real routes.
- **Mine the redirect allowlist in the bundle.** Grep the JS chunks for an array of route strings (`["/login","/cadastro",…]`) — an auth redirect helper's allowlist enumerates the app's public routes in one read.
- **The registration endpoint is in the form component, not the markup.** A React registration form has no `action`; the endpoint is a `fetch`/`axios.post` inside the component chunk. Grep the bundle for the component name and read the call site to get the URL, method, and body fields. `GET` on that URL returning `405` confirms the route exists and is POST-only without sending a POST.
- **A hidden link is not a disabled route.** A login page can pass a `registerNewUser:false` flag that hides the signup link while the signup route still answers `200`. Probe the route directly; do not conclude "registration disabled" from the rendered link.
- **DesignCompose / `x-dc` apps ship the whole component and its state in the served HTML.** The `<script type="text/x-dc" data-dc-script>` block contains the `DCLogic` class, the initial `state` object, and the `renderVals()` mapping. Read the inline state for default field values and the `renderVals` mapping to learn which template placeholders bind to which state key.
- **An SPA catch-all answers `/robots.txt` and `/sitemap.xml` with the app shell.** A `200 text/html` the size of the homepage is the shell, not a robots file. Check `content-type` and compare the body hash against `/` before reading directives.
- **Distinguish RSC streaming noise from personalization.** Repeated fetches of the same Next.js page vary in byte length because the RSC chunks stream in a different order. Diff two captures; if only the chunk ordering differs, there is no per-user content or token — do not report a phantom CSRF nonce.
- **Read the post-login app shells to map client routes.** A client-side app served unauthenticated at a post-login path (e.g. a home/dashboard) exposes its full route table and endpoint inventory in the HTML. Grep for `'/path'` literals and `api('/…')` calls to build the client route map without an account.

## Legacy vs current platform (read-only)

- **Tell the legacy e-commerce platform from the current storefront by the session cookie and the route family.** The same brand can expose an old and a new commerce stack side by side. The old one shows a `JSESSIONID` (Java) and a `*_Loja.html` action family (`carrinho_Loja.html`, `comprarAgora_Loja.html`, `edit_ClienteLoja.html`) plus `/manager/*`; the new one shows a `vtex_session_id` (or another platform's cookie) and a `/_next/static/...` Next.js bundle. They are separate systems — do not treat one as the other.
- **A login page that `302`s to `/404` is not served; read it from the archive instead.** When `<host>/manager/login_*.html` redirects straight to a 404 page (and still sets a session cookie and an app `version:` header), the page is missing or the flow is gated. Read the rendered form from the Wayback capture (`web.archive.org/web/<ts>id_/<url>`) and confirm no signup link in its `<form>` and anchors — do not conclude "registration exists" from a declared-but-unused `recaptchaCadastro` variable.
- **A legacy app's vendor and tenant mix hide in its static assets.** The error/login pages reference the app's CSS/JS by path (`/<app>/styles/page404.css`, `jquery.X.Y.min.js`). Fetch the CSS; a minified stylesheet often carries another tenant's brand classes (`.brandProduct`, `.modal-brand-btn`) and absolute CDN URLs on the platform vendor's domain (`cdn-<brand>.<vendor>.com`) plus a vendor-logo class. This confirms a white-label/multi-tenant platform without touching another tenant. A referenced JS that now `404`s is a negative, not a finding.
- **Map a legacy app's route inventory from its own `robots.txt`.** A legacy host's `robots.txt` (`200`) commonly lists the old action family (`*_Loja.html`, `checkout`, `fidelidade`) that no longer appears anywhere else — a discovery aid worth an `info` entry, distinct from the current storefront's robots.
- **Inventory a legacy platform's routes from the CDX, not from guessing.** `curl -g "http://web.archive.org/cdx/search/cdx?url=<host>&matchType=host&output=text&fl=original,timestamp,statuscode&collapse=urlkey&filter=original:.*/manager/.*"` lists every archived path under a module. Two paths ever archived under `/manager/` (a login and a panel executor) is stronger evidence of "no registration route" than any amount of targeted probing. Use `-g` so curl does not choke on `[` in the filter.

## Misrouted / stale subdomains (read-only)

- **Read the presented certificate to find a misrouted host.** `curl -sS -k -D - -o /dev/null https://<host>/` on a client subdomain; if the TLS subject/issuer belongs to a different organisation (a `.com` of another firm), the record points at a shared/agency host serving another tenant. The HTTP body often confirms with a product default route (e.g. an ASP.NET Core `/Identity/Account/Login` redirect).
- **A public DNS record with a private address is a finding without a probe.** `dig +short A <host>` returning `10.x`/`192.168.x` plus a CNAME to `internal-*.elb.amazonaws.com` publishes internal topology. One `dig` (repeat to confirm) is the whole test; the host is not reachable from outside by design.
- **Confirm a dangling CNAME against the target's authoritative NS.** The parent may still answer `NOERROR` with the CNAME while the target is `NXDOMAIN`: `dig <host> @<authoritative-ns> CNAME` and `dig <target> @<target-zone-ns> A`. A target under the provider's own domain is not third-party-claimable — rate it as stale DNS, not takeover.
- **A wildcard certificate avoids publishing the subdomain list.** When the current cert is `CN=*.target.tld`, CT does not enumerate per-host names from it — treat CT as a floor and use passive DNS/Wayback to widen, rather than reading the wildcard as a narrow surface.

## Client-rendered shells and internal API mapping (read-only)

- **Read the SPA shell's `api()` wrapper to map the whole internal API.** A client-rendered app served unauthenticated at a post-login path (e.g. a DesignCompose `x-dc` shell) contains one wrapper that prefixes the API base (`/api/v1`) and injects the bearer token from storage. Grep every call site for the literal path and the `method:` option — the set is the full authenticated surface, with methods and bodies, without an account. Confirm the boundary with a bounded `GET` per resource: `401 Bearer` on all of them means the API is the authorization boundary.
- **Read the role matrix from the menu gates.** Grep the shell for the profile enum map (`{Admin:'Administrador', …}`), the nav builder (`isAdmin ? [...] : [...]`) and the page guards (`adminOnlyPages`). The per-profile menu plus the `canManage*` booleans give the intended RBAC; label it inferred until a test confirms the server enforces it.
- **Map a ticket-based SSO handoff from the client.** Grep for `sso-ticket`, `sso-exchange`, and `#ticket`; the client shows the ticket is one-time, short-lived, and passed in the URL fragment (never sent to the server). The confirmation tests are: replay the ticket, call a write endpoint directly with the impersonation bearer, and call the ticket route with a lower role.

## Subdomain wordlist enumeration (authorized active)

- **Brute-force the zone with a service/infra wordlist plus permutations of known hosts.** Build ~250 common names (`jenkins`, `grafana`, `ldap`, `registry`, `kibana`, `staging`, `flow`, …) and add prefix/suffix permutations of every host name already known (`<host>-dev`, `dev-<host>`, `<host>-hml`, `<host>2`, …). Query each `A`/`CNAME` against two public resolvers.
- **Distinguish `NXDOMAIN` from a resolver error before counting.** A `connection timed out; no servers could be reached` is a resolver failure, **not** a negative. Parse the answer's `status:` field and re-query failures on the other resolver; counting a timeout as "not resolved" misses hosts and counting it as "resolved" invents them.
- **Re-probe a wildcard before trusting any hit.** Query three random labels; if none resolve, each hit is a real record. A wildcard makes every candidate look alive.
- **Wordlist beats CT when the certificate is a wildcard.** A `*.domain` certificate never publishes per-host names, so `crt.sh`/Cert Spotter show the floor, not the surface. Names like a monitoring stack or a CI host routinely appear only in DNS — always run the wordlist in addition to CT.

## Light port scan without nmap (authorized active)

- **One connection per port, bounded, and state-labelled only.** Use Python `socket.connect_ex` with `settimeout(2.5)`; run one thread per host, `time.sleep(1.0)` between ports (≤1 req/s per host). Classify `rc == 0` → `open`; `ECONNREFUSED` (Linux 111, macOS 61) → `closed`; anything else → `filtered`. No banner grabbing, no retries, no UDP.
- **Scan the client's dedicated IPs, not the shared CDN edge.** A client name on a third-party edge (CDN/WAF) resolves to shared infrastructure — port-scanning it tests the vendor and hits other tenants. Restrict the scan to IPs the client actually owns (datacenter ranges, cloud project IPs) and state the exclusion.
- **A full `closed` row proves the host is up but has no listening service.** All ports `closed` (RST) means the host is alive and reachable while exposing nothing on the scanned list; a mix of `filtered` means a firewall drops silently. Do not read "no open port" as "host down".

## Grafana unauthenticated recon (read-only)

- **Read `/api/health` first — it is unauthenticated and returns the exact version.** `GET /api/health` → `{"version":"X.Y.Z","commit":"…","database":"ok"}` proves product, version and DB liveness in one request. Then map the boundary: `/api/search`, `/api/user`, `/api/org`, `/api/frontend/settings`, `/api/snapshots`, `/api/datasources`, `/api/admin/settings` all returning `401 {"message":"Unauthorized"}` proves anonymous access is disabled (a positive control).
- **`/metrics` is a separate, often-forgotten endpoint.** `GET /metrics` (Prometheus, `text/plain`) is unauthenticated when `metrics.enabled=true` and no basic auth is set. `grafana_build_info{edition="…",version="…",goversion="…"}` reveals the edition (OSS vs **Enterprise**) and exact version; the body also lists the API handler inventory, feature toggles and alerting/DB metrics. Treat its disclosure as `baixo` (operational metadata, no PII).
- **`/signup` returning the SPA shell proves nothing.** Grafana serves the same `index.html` for every frontend route. Whether self-registration is enabled is only decidable by `POST /api/user/signup` (state-changing — not allowed read-only) or by `/api/frontend/settings` (which is `401`). Record it as untested.
- **Filter the CPE result by the exact vendor range.** The NVD CPE query over-includes: `cpe:2.3:a:grafana:grafana:9.5.1` returned 25 CVEs, but only 19 have `9.5.1` inside the vendor's affected range — the rest sit on ≥10/11 branches. Read each CVE's `affected[].affectedData[].versions[]` and test `version <= target < lessThan`; do not attribute the whole CPE list.

## Internal-service DNS wordlist (read-only)

- **A wordlist of internal/DevOps names finds the private topology that a service wordlist misses.** Query ~100 names (`nexus`, `sonarqube`, `portainer`, `vault`, `consul`, `argocd`, `jira`, `prometheus`, `logstash`, `minio`, `etcd`, …) as `A`/`CNAME` against two public resolvers. Names resolving to `10.x`/`172.16–31.x`/`192.168.x` or to `internal-*.elb.amazonaws.com` / `nlb-*…elb.*.amazonaws.com` publish the internal inventory.
- **Confirm by DNS only; never contact the private address.** A public record that answers with an RFC1918 address is the finding on its own. Do **not** resolve-then-connect — the host may be unroutable and contacting it violates the "no private target" rule. One `dig` (twice) is the whole test.
- **Distinguish the internal load-balancer families.** `internal-devops-…elb.amazonaws.com`, `internal-registry-…elb.amazonaws.com` and `nlb-devops-…elb.*.amazonaws.com` are three distinct internal endpoints; each groups a set of service names (CI, artifact registry, container tooling). Record the mapping.

## Post-registration access-control tests (authorized active, one account)

- **The registration response may carry the credential itself.** Read the success body before assuming the flow sends an email: a signup endpoint can return an auto-login link (`…/magic/<code>` or `…?code=…`) that authenticates directly. When it does, the token is in the HTTP response (log/history/devtools) and the account may be created with no email-ownership proof — two distinct findings (token exposure; no verification).
- **Test the auto-login credential for single-use and entropy, once authorized.** Exchange it, then exchange the same value again on a clean client state. A second success means the token is **replayable**; record its length. Pair it with a negative control (a bogus value must be rejected).
- **Reconstruct the exchange from the client bundle, not by hand.** A NextAuth app posts to `/api/auth/callback/credentials` with form fields `csrfToken` (from `/api/auth/csrf`), the identifier, the password **or** the magic `code`/`token`, and the tenant id, plus `json=true`. The browser flow uses `signIn("credentials", …)`; the raw callback is the same request.
- **Read the provisioned role from the session, then probe privileged routes.** `GET /api/auth/session` gives `user.role`. With that session, request the admin/manager routes and role-gated APIs: a `404`/`403` proves the gate; a `200` on a privileged page is vertical escalation. Do not guess IDs — only a foreign known identifier proves horizontal BOLA.
- **Test a magic-link `next`/redirect parameter by observing the `Location` only.** Send the link with a curated `next` set (external URL, `//host`, `/\` and `\\`, `javascript:`/`data:`, `%2F%2F`/`%5C`, double-encoded, absolute same-origin, internal paths, the client allowlist, `../`, `/%2e%2e/`) using `curl --max-redirs 0` and no `-L`; never follow to a third party. A `Location` built from server-side constants plus a resolved id (with none of the payload reflected) is the control. Treat a special keyword (e.g. `next=reset`) that routes to an internal auth page as a branch, not an open redirect.
- **A magic-link code can be bound to a purpose — test it against the reset endpoint.** When `?next=reset` lands on a password-change page, the client form usually posts only `{password, passwordConfirm, code}` (no current password). Do not assume the login code works there: `POST` the reset endpoint with the login code and read the error. A rejection (`"link invalid/expired"`) proves purpose-binding, which downgrades the replayable-token impact from account takeover to session issuance. Confirm the same code still authenticates via `signIn` as the positive control, and verify the account password is unchanged by logging in with the original password.
- **Grepping a `safeRedirect` helper is not enough — read its call sites.** A client redirect helper that tests `startsWith("//")` before `new URL()` normalization can still return a `//`-leading path (`/a/../..//evil`) after the browser normalizes it. It is an open redirect only if a caller assigns the raw return to `location`; when every call site does `location.replace(\`${origin}${value}\`)`, the origin prefix anchors it same-origin. Report the latent normalization edge as `info`, not a live open redirect.

## Object-trust and authorization probes (authorized active)

- **Distinguish a session-scoped update from a client-supplied-id update with a two-request differential.** Send an authenticated update endpoint the session user's own `id` and then a **non-existent** id, with no data fields. Own id → `200` (updates you); non-existent id → an ORM "record not found" for the `update` proves the **where used the body id**, not the session. A response that instead updates the session user (no "not found") proves session-scoping. No write occurs on the invalid-id request, so this is a minimal-proof BOLA test.
- **Read the ORM error to see which key is authoritative.** A nested-relation error such as `No 'XOnY' record was found for a nested update` names the relation and shows the second key (e.g. a tenant id) is part of the write, while the object id came from the client. The error text maps the authorization boundary without any state change.
- **A global fallback authorization policy makes every path answer the same denial.** An ASP.NET Core / Kestrel API that returns `401 WWW-Authenticate: Bearer` for **unknown** paths too (not `404`) has a fallback policy — Swagger/actuator/metrics are covered even though their routes are not mapped. The single unauthenticated exception (often `/health`) is the whole public surface; do not read the uniform `401` as "route exists".
- **Confirm tenant isolation by tampering the tenant parameter, not the path.** Call the same endpoint with the session's tenant and a syntactically valid foreign/absent tenant; `401` or an explicit `{"error":"...not linked to..."}` proves the server matches the token tenant, while a `200` with foreign rows is the break. Do the same for missing-parameter handling — a bare `500` is a robustness gap (should be `4xx`).
- **An in-app auth endpoint that `307`s to a vendor domain is a dependency/branding signal, not a takeover.** Observe the `Location` only (never follow it to the vendor); record that the client's own login flow hands the user off-domain, and keep the vendor's systems out of scope.
- **Promote the object-trust differential to a confirmed write IDOR with a second test account you own.** The mismatched-id error is only a hypothesis. When the RoE authorizes a second account: (1) register account B; read B's current state through B's own session; (2) with account A's session, send the update endpoint B's `userId` in the body `id` and a **benign, distinguishable** value in a low-impact field, preserving B's other fields; (3) re-read B's state **through B's session** — a change proves the write targeted B, not A; (4) restore the field through B's session and re-read to confirm the original value; (5) record both accounts' ids for the client to delete. Never target a real user's record.
- **Read the write endpoint's success body to see which object it returns.** A BOLA write that returns `{"user":{"id":"<target>"}}` — the target's id, not the caller's — confirms the subject was the client-supplied id. Combine with the victim-session read-back for the full proof.
- **Test the tenant dimension of a body-keyed write with a negative control.** Send the update with the victim id but a **foreign/inexistent** tenant: a `200` carrying an ORM "record not found" (not an authorization denial) shows the only gate is the existence of the `(id, tenantId)` row and that the caller's session tenant is never checked. State that a true cross-tenant write remains inferred unless a second tenant you own is available.

- **Separate an "unknown route" from a "protected route" under a fallback-auth API.** When every unauthenticated request returns `401 WWW-Authenticate: Bearer`, the status alone cannot tell a mapped-but-protected route from an unmapped one. Compare the **body**: public/mapped auth routes answer `application/problem+json` or `application/json` with a message, while unmapped/protected routes return an **empty-bodied** 401. A non-empty body is the signal that the route exists; the empty 401 is the fallback. One `POST` with a synthetic body per candidate is the whole test.
- **Confirm an enumeration oracle with a random valid-format control before believing an "active account".** A reset endpoint that returns `usuarioAtivo:true` may only be echoing that the identifier passed a checksum. Generate a **random identifier that passes the format/checksum** (e.g. a valid random CPF) and send it: `false` for the random value and `true` for the target proves the oracle is content-based and the target account is real. Without the control, `true` is not evidence of existence.
- **Read a reset session-token's structure locally.** Base64-decode each segment: a shape like `base64("<index>:<ticks>").base64("<signature>")` with the server timestamp in clear is a design detail, not a secret. A step-2 endpoint that answers a **uniform `200`** to an intact, a tampered, and an out-of-range token is anti-enumeration — it does not prove the signature is unchecked. Never send the token of a real account to trigger its e-mail.
- **A shared edge routes by `Host`, not by SNI.** Sending `Host: <other-vhost>` to one IP returns the other app's shell (normal reverse-proxy behavior, not a finding); an unmatched `Host` usually returns a bare `404 page not found`. Do **not** enumerate Host values — that is virtual-host fuzzing and is out of scope.

## Measuring reach without harvesting (authorized active)

- **A leaderboard page and a comments API are the two cheapest member-count oracles.** An SSR leaderboard (e.g. `/ranking`) renders member display names in its RSC flight payload (`["$","li","<name>-<index>",{…}]`) even when the page makes no visible API call; a comments feed returns an author object (`userId`, `user.tenants[].name`, `picture`) per row. Both hand a member list to any authenticated user.
- **Bound the sample and state the cap.** Paginate the feed to a fixed small depth (e.g. 3 of the server-reported `totalPages`), count **distinct** ids/names, and report "at least N". Never page to exhaustion. Cross-check the leaderboard for the same names to widen the union without extra requests.
- **Read the leaderboard from the RSC payload, not the DOM.** `grep` the streamed `self.__next_f.push` payload for the row element key (`["$","li","…-0",{`); a page that returns no `/api/` literal in HTML can still embed every row server-side. Test whether `?page=`/`?offset=` changes the list to tell a fixed top-N from a paginated full list.
- **`totalPages` is not a member count.** A paginated comments response reports pages of comments, not distinct members and not a tenant total. Say so explicitly; do not convert it into a member total.
- **Test the read-side for full PII with the write-endpoint differential, not by fetching.** Reuse the invalid-body trick on sibling endpoints: the ORM `where` in the error names the authoritative key (`where: {id: <body>}` = client-controlled BOLA; `where: {userId: <session>}` = session-scoped). This distinguishes a write-IDOR from a session-scoped control with no write and no read of third-party data.
- **A `GET` that only returns `{success}` can still be a client-controlled action.** An OTP/trigger endpoint that takes `userId` and validates only the `(userId, tenantId)` link (not the session) can act on another member. Do not fire it against a real member to confirm — the side effect is an email to a third party; record it as inferred and name the test that would confirm it with an account you own.

## Rules of engagement for every technique

- `GET`/`HEAD` only unless an authorized active test says otherwise. No credentials, no bodies, no mutations.
- One request per probe; never mass-scan. Rate-limit any active test and respect the agreed window.
- Cross-check a version with a second source before attributing a CVE.

## Gamification point-integrity analysis (read-only)

- **Extract the action→points map from the rendered page and the client `actionMap`.** On a Next.js/React app the gamification page renders each action label followed by `+ N PONTOS` (regex the label `<div>` then the `+<!-- -->N<!-- --> PONTOS` cell). The bundle holds an `actionMap` of action keys to labels (`login`, `mark_lesson_as_read`, `comment_in_lesson`, `complete_course`, `generate_certificate`, `post_in_community`, `like_in_post`, …). The page gives the points; the bundle gives the mechanism.
- **Read the point history to see the crediting model.** A "Histórico de pontos" that shows `Action · N x + N` proves **per-event crediting with no per-object idempotency**. Combine with a confirmed missing-validation write (fabricated id accepted) to show unbounded farming.
- **Find the client-side guard.** Grep the gamification provider for `localStorage`/cookie checks around the credit call; a guard like `localStorage.getItem("login") !== <today>` is the only once-per-day control — the server must be tested separately, or the finding marked inferred.
- **Distinguish once-only from per-event by object validation.** Sibling endpoints that validate the object (`certificate/verify` → "not found", `quiz/start` → 404) are once-only; the one that accepts a fabricated id (`lesson/read`) is the farm.
- **Do the whole mapping without crediting a point.** Read the page and the bundles; use the API only for `GET`s. Any credit-bearing write is a residual on a test account — avoid it unless the RoE explicitly allows the minimum observation, and declare it.
