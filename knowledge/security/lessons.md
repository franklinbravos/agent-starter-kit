# Lessons — Mistakes and Rules Learned

Each lesson is a mistake that cost something or a rule that changed how we work. Add one entry per engagement review.

## Authorization and scope

- **A pasted URL is intent, not authorization.** Before any active test, obtain written scope: who authorized it, the assets, the window, and the prohibited actions. Without it, the engagement is passive OSINT only.
- **A client's vendor is a third party.** Testing a vendor without separate authorization is out of scope, even when the client owns the data. Vendors are OSINT-only.
- **Report the scope you actually had, not the scope that sounds impressive.** State what was excluded and what remains unconfirmed.
- **Ownership is per-domain and per-TLD, not per-brand.** A client owned the `.com` domain, while an unrelated `.com.br` domain of the same brand belonged to a different company. Verify each domain separately through WHOIS; never infer ownership from a matching brand, a sibling domain, or a certificate organization alone. An attributed domain is probed; an unattributed one is OSINT-only.

## Evidence and accuracy

- **Verify the affected range before attributing a CVE.** A version can be the one that *introduced the fix*. Example: GitLab 16.8.1 is the patch for CVE-2024-0402, not a vulnerable version — reporting it as a flaw would have been a false positive.
- **The newest patch level is not proof of safety.** Magento 2.4.7-p10 was current and still exposed to CVE-2026-75650 until an out-of-band hotfix. Distro backports further break the version→CVE mapping.
- **Separate confirmed from inferred.** A route that "looks guarded" is inferred until a test confirms it. Label it and name the test that would confirm it.
- **Let evidence downgrade a finding.** A public signup form looked like an open door; the manual test showed accounts require administrator approval. The finding moved from crítico to médio — the report became truer.
- **A `200` from an SPA is not a file.** An SPA/Vercel catch-all returns `index.html` (200) for `/.env`, `/graphql`, `/api/health`, and `*.js.map`. Check `content-type` and byte size before calling it an exposure — a ~900-byte `text/html` response for `/.env` is the app shell, not a leak.
- **A docs/spec probe that returns the app shell is a negative, not "docs exposed".** A SPA catch-all answers `200 text/html` for `/api`, `/docs`, `/swagger`, and `/openapi.json`; the payload is the same `index.html`. Diff the body (or its length) against the homepage before rating — a real `openapi.json` is `application/json` and starts with `{"openapi"`.
- **`dig +short A` prints the CNAME target when the final A record is missing.** A resolver answering with a hostname in the A lookup is not a resolution — it is a dangling CNAME. Build the "active host" test on a real IP (`first_ip()`), never on a non-empty answer string; otherwise every dangling CNAME looks alive.
- **DNS answers can be inconsistent mid-propagation.** Two queries minutes apart returned a cached CNAME for a host whose authoritative servers no longer served it. Query the authoritative nameservers *and* two public resolvers, keep both snapshots, and record the discrepancy honestly instead of picking one.
- **Anonymous object-storage listing is medium, not automatic critical.** A CDN bucket exists to be read; the misconfiguration is the *listing*, which exposes the whole inventory and any `int-`/`dev` namespace. Read one page of the XML, confirm no secret/PII, and rate on that evidence — public marketing assets are medium; any credential or personal data makes it high.
- **An unprotected framing directive and a dead one look the same in a header dump.** `X-Frame-Options: ALLOW-FROM <uri>` is ignored by modern browsers, and `frame-ancestors;` with no value is an invalid directive that is also ignored. Both are findings; neither is a control. Read the directive's value, not its presence.
- **A wildcard certificate under a third party's domain is a dependency to name.** When the apex and `www` serve `CN=*.agency-domain` with a SAN of `*.target.tld`, the target's wildcard is issued inside the agency's certificate account. Report it as an ownership/redundancy observation, not as a vulnerability — but do not omit it.
- **A public publishable key is not a secret.** Supabase `sb_publishable_…` and legacy anon JWTs ship to every browser. Report them only when a table or RPC returns data the caller should not see (RLS off), never on the key alone.
- **Open signup + auto-provisioning is an access path, not a registration nuance.** A Supabase `disable_signup:false` becomes serious when a trigger grants roles/permissions at signup — a self-registered outsider becomes an authenticated, provisioned user. Test what the new user can read (RLS by role), not just whether signup succeeds.
- **Email confirmation is not authorization.** When signup requires email confirmation, that only proves the address is reachable — a public/disposable inbox completes it. The real gate is what the confirmed user is allowed to do.
- **A tenant column the user can write is not an access control.** When RLS keys off a field the client can UPDATE (e.g. `profile.organization_id`), any authenticated user can switch tenants. Test it: write the target tenant id into your own row, then re-read the scoped table — a count moving from 0 to N is a cross-tenant break.
- **Prove INSERT permission without creating a row.** POST `{}` to the table; a `42501` (RLS) means blocked, while a `23502/23503` (constraint) means RLS allowed the insert and only the data was invalid. The constraint error proves the write path is open with no data left behind.
- **Ticket content is a credential store in disguise.** Service desks accumulate API keys, session tokens, and passwords in descriptions and comments. Once you can read tickets (via tenant hop or an RLS gap), scan the text fields for secret patterns and cross-reference project refs — a leak is a lateral-movement path. Validate a leaked key read-only (does the endpoint answer?) but never log in with leaked passwords during an assessment.
- **Confirm the secret type before reporting it.** A `service_role` string can be a remediation note, an anon key is public by design, and a session token may be expired. Decode the JWT payload (role/ref/exp) and probe read-only to classify — only a valid, privileged credential is a critical finding.
- **Leaked test credentials usually target a staging preview, not production.** QA notes reference the preview URL they tested (`*-<name>.vercel.app`); identify the app's auth library (Supabase `signInWithPassword` vs Better Auth `/api/auth/sign-in/email`) and test there. Watch for `429` — a sign-in rate limit is a control, not a failure: stop rather than hammer.
- **Inventory attachments by metadata even when files are not downloadable.** The `attachments` table exposes names/types/sizes; `xlsx`/`pdf` entries indicate HR/financial PII even if storage RLS blocks the download — report the exposed metadata and confirm the storage boundary separately.
- **Confirm the shipped plugin version from the vendor's own asset, not only `readme.txt`.** The Stable tag can lag; the plugin's `?ver=` and the banner in its minified JS reflect the installed code. A bundled library's version (e.g. a `particles.js?ver=3.0.6` path) is not the plugin version — using it flips a finding false.
- **Spend a one-request-per-host budget on the most informative path, not the root.** A non-invasive engagement that allows a single `HEAD`/`GET` per host must send it to the path the brief actually names (a login/SSO route), not `/`. The root returns the SPA shell and reveals only the front proxy; the named route reveals the app's auth behavior. Sending the only request to `/` wastes the budget on the least informative path and forces a "not tested" limitation.
- **A historical wildcard certificate makes Certificate Transparency a floor, not the surface.** When `crt.sh` shows `*.domain` issued in the past, every subdomain that was only ever covered by the wildcard is invisible to CT; the current per-host certificates list only the names that exist today. Never present a CT-only name count as the total external surface — label it the minimum and name passive DNS as the next source.
- **A reflected `Origin` with `Access-Control-Allow-Credentials: true` is worse than `*`.** The wildcard is rejected by browsers when credentials are present; reflection actually grants cross-origin reads. Report the reflection on its own, not under a generic "permissive CORS" line.
- **Check core↔plugin compatibility for availability, not just CVEs.** A plugin can be fully patched and still fatal-error against a new core major (WordPress 7.1 + WP Rocket < 3.23.2.2). A live homepage does not prove the condition is absent.
- **Email possession is not authorization.** Supabase password recovery to a **public/disposable inbox** completes the identity loop. A public signup or a public inbox turns "verified e-mail" into a self-service credential — the gate must be the role/provisioning, not address reachability.
- **A private bucket can still leak through a writable-tenant hop.** Storage RLS keyed to `profile.organization_id` is only as strong as that column's immutability. Test the app's real bucket and path, then hop; an object that is "not found" at `organization_id:null` becomes downloadable under another tenant.
- **A `SECURITY DEFINER` RPC that fails on a foreign key has already passed authorization.** The `23503` proves the function reached the INSERT/UPDATE. Do not mistake the constraint failure for a control — test with a non-existent UUID and read the error, never with a real record.
- **Revalidate a prior "blocked" claim against the exact object before repeating it.** "Attachment download is blocked" was true for the `attachments` bucket and false for a second, differently-scoped bucket; naming the wrong object would have buried a real finding.
- **An exposed origin is not automatically "alto".** A leaked backend reachable directly (CDN/WAF bypass + plaintext HTTP + internal hostname disclosure) only rates high when it serves non-public surface. Confirm read-only what the origin actually answers (`/api`, `/admin`, auth paths) before rating; if those `404` on the origin, the impact is public content and the finding is `médio`. Same discipline as the GitLab fix-version false positive — evidence sets the severity, not the adrenaline.

- **CT/DNS brute-force only see the live surface; the Wayback CDX sees what was removed.** A domain's most sensitive historical exposure (a legacy HR portal, a decommissioned admin) often has no current DNS record and no individual cert, so `crt.sh` and brute-force miss it. The CDX `matchType=domain` call surfaced a legacy recruiting subdomain and a decommissioned portal that were NXDOMAIN — those were the real finds of the phase, not any live host.
- **A `.js.map` with no secrets is still a finding.** The exposure is the source itself (structure, controller names, internal naming). Grep the `sourcesContent` for keys/buckets/hostnames to set severity, but report the map exposure regardless.
- **Client-side keys are not database keys — classify before escalating.** A Google Maps `AIza…`, a reCAPTCHA site key, and a New Relic browser `licenseKey` are all `public-by-design` (embedded in client code) and none grants access to a database or to the client's data. Report them for the *billing/quota-abuse* angle (unrestricted `referer`) only, and name the third-party-console test that would confirm the restriction — never call them a "leaked database key".

- **Decode a hardcoded token before calling it a leaked secret.** A literal JWT in a production front-end bundle is a credential-management smell, not automatically a high. Read the `iss`, the claims, and the `exp`: a token from a vendor *sandbox* issuer, naming an example merchant, and already expired has zero live impact — rate it low/info and flag the pattern, not the token.
- **A public-by-design key is only a finding alongside an open data surface.** A Firebase web API key, a reCAPTCHA site key, a OneSignal app id, and an Azure tenant/client id all ship to every browser. Report them as inventory; escalate only when the key reaches a database or function that returns data the caller should not see (e.g. open Firestore rules).
- **The development `environment` object can ship inside a production bundle.** Angular ships `environment.ts` at build time; an `apiUrl` of `http://localhost:8080/api` or an MSAL `redirectUri` of `http://localhost:4200` in a production artifact is a misconfiguration — verify the redirect URI is not registered on the production identity provider.
- **A single HTTP method does not characterize a route.** A `GET`/`HEAD` that returns `401` proves the *read* path needs auth; it says nothing about whether `POST` (sign-up) is public. Do not upgrade or dismiss a registration finding from one method — label the untested method inferred and name the test.
- **An active-account record is not the same as a usable session.** A signup that returns `is_active:true` still blocked login with "not confirmed": the app-level flag and the identity-provider state are independent. Report the two separately — the flag as a provisioning observation, the login gate as the real control — and do not rate the flag as if it granted access.
- **Compare every server timestamp to the transport clock.** A body field suffixed `Z` looked like UTC but matched local time exactly (−03). One look at the response `date:` header (GMT) proved a 3-hour serialization bug that would silently skew any audit trail. Read the clock, do not trust the label.
- **Measure what signup actually provisions before rating open registration.** After confirming the account, read the login `type_user`/`role` and the profile: an auto-provisioned `Guest` with `contract:false` and no entitlement flags turns "open registration" from a medium access-path finding into a low one. The confirmed scope of the provisioned account — not the excitement of creating it — sets the severity; the residual access question is a separate, explicitly-authorized test.

- **The real new surface often hides behind a shared IP, not a shared name.** Certificate Transparency and DNS brute-force see only names that share the brand. A reverse-IP lookup on the client's own origin surfaced a sibling company's hostname that CT and brute-force had never shown; the shared droplet plus public company-registry data (same partners, same address) proved the relationship. Pivot on infrastructure, then verify ownership in the registry.
- **A brand is not a domain — check the domain before citing breach data.** A public breach report named the client's brand; the affected domain belonged to an unrelated company in another country with a coincidental name. Verify the exact domain (WHOIS/RDAP) before attributing any leak, or the report invents a breach.
- **A domain's own WHOIS technical contact frequently owns the netblock that hosts the "intranet".** An IP whose LACNIC owner and abuse contact matched the target domain's technical contact was in-scope infrastructure, even though it carried a third-party PTR. Read the RIR record, not the reverse DNS name.
- **A strong SPF/DMARC/DKIM on the primary domain does not cover the group's other domains.** The related domains had SPF `-all` but no DMARC and no DNSSEC, and the DKIM key was 1024-bit. Enumerate the whole domain portfolio — the posture of the apex is not the posture of the group.
- **Report the absences too.** DNSSEC off, MTA-STS/TLS-RPT/BIMI missing, and CAA absent are inventory, not noise; they are the cheapest fixes and belong in the findings register alongside the version gaps.

- **An exposed remote-access gateway with an unknown firmware is an exposure finding, not a CVE.** A FortiGate SSL-VPN (`Server: CPWS`) or a Citrix NetScaler (`NSC_*` cookies) reachable from the internet is `alto` on exposure alone, but the product name proves nothing about the patch level. State the exposure, record the version as unknown, and name the authenticated read that would confirm it — attributing a CVE from the banner would be fabrication.
- **A hostname that leaks in `robots.txt` and resolves in the client's own block is live surface, not history.** CT lists issued certificates; it does not list hosts that never got a public cert. Cross-check robots `Disallow` names against DNS and the client's IP block before writing them off as noise.

- **A passive subdomain aggregator inflates the surface with permutations — resolve before you inventory.** An aggregator returned names with appended single letters (`campus7`, `agents-weug`, `flexxsignpre1`) that had no DNS record. Counting them as assets would have tripled the reported surface. Dedupe every candidate against CT and Wayback, resolve each with `dig`, and keep only names with a current record; label the rest as historical noise.
- **A wildcard DNS zone makes every candidate look live.** Before treating a resolution as a new asset, probe a random label. If the random label resolves, the zone has a wildcard and the resolution proves nothing. Confirm the negative probe first, then count.
- **Certificate Transparency is a customer list when certificates are issued per tenant.** A SaaS that issues `<customer>.workspaces.<domain>` certificates publishes its client names. Report the naming and the tenancy disclosure as business-confidentiality information at `info`, and do not dress it up as a vulnerability — it is inherent to public CT.
- **Registration keywords on a login page are not a signup route.** An LMS/portal login page can be full of "registro"/"alta"/"nuevo usuario"/"crear cuenta" strings that are *admin-panel* translation keys ("enroll a student"), not a public self-registration form. Before obtaining a mailbox or POSTing, read the page's own markup — the `<form>` fields, every `<a href>`, and the login JS bundle's `public/...` AJAX endpoints. If no signup form, link, or endpoint exists, self-service provisioning is admin-gated and the "active-before-verification" question is moot; report the gating as a positive result instead of inventing a weakness or fuzzing for a route.
- **A registration hunt must cover the whole app portfolio, not the first app.** One app had no signup; four other SPA/PRM bundles carried `register`/`SignUpPage`/`createAccount` strings that belonged to feature flags, endpoint registries, and a third-party partner platform. Checking only one app would have left the conclusion unproven and the authorized test unexercised. Read the root and the client bundle of every client app, then state the portfolio-level result as a single positive finding.
- **A client-side route that returns `200` for `/signup` is a shell, not a form.** SPAs answer every path with the same `index.html`; a `200` on `/register` or `/partner-onboarding` proves only client-side routing. Diff the response body against the homepage and check for a `<form>`, an endpoint, or a POST handler before calling a signup route present.
- **A third party's signup is not the client's signup.** When the only registration flow in a client app is hosted by a SaaS (e.g. a partner-relationship platform's onboarding page), record it as a third-party surface and keep it out of scope without separate authorization — the client's own apps may still have none.

## Testing discipline

- **Never guess credentials or create accounts on production.** Try a password and you are conducting an attack; create an account and you are mutating live data. Both need an authorized test environment.- **Do not confirm a vulnerability by exploiting it unless authorized.** Reachability and version evidence is enough for a finding; exploitation belongs in an authorized, controlled test.
- **Read the error, then trace the data flow.** Verify that untrusted input actually reaches the sink before calling it a vulnerability.
- **Settle mass assignment by the echo, not the payload.** When a create response returns the protected field, compare it against the value sent. Sending `role:"Owner"` and reading back `role:"Guest"` proves the field is whitelisted — no second payload and no login required.
- **Check uniqueness on every identity key, not only the login key.** A signup that rejects a duplicate e-mail but accepts a duplicate national ID (CPF) creates an identity collision. When a reset flow resolves the account by that document, the collision is a plausible takeover path — test each identity key separately and rate the duplicate-key acceptance, not just the enumeration oracle.
- **A public confirm endpoint tells you what its code field must be.** Probing an identity-provider confirm route without the code returns the upstream validation error (e.g. Cognito `$metadata`/`requestId`/function name). That both maps the required field and proves the backend leaks IdP internals — report non-authenticated reachability and the verbose error as separate evidence.
- **The upstream error names the parameter the API actually read.** When a confirm route rejects with `Value null at 'confirmationCode'`, the value sent under `confirmationCode` never reached the provider — the API reads a different field (`code`). Retry with the provider's parameter name before concluding a secret is missing; the field-name mismatch is an API-contract fact, not a missing-code fact, and it changes the verdict.
- **Scrub every token, not just the one you remembered.** A login response carries an access token *and* a refresh token; replacing only the access token leaves the refresh token in the transcript. After any authenticated capture, scan the whole workspace for long `eyJ…` strings and for every password value used, and confirm zero remain before the handoff — the integrity rubric fails on one leaked secret.
- **A magic-link token may be bound to a purpose, so test it against every endpoint that consumes it.** A `?next=reset` link that lands on a password-change page does not mean the login code resets the password: the reset endpoint rejected the magic code (even with a valid session) while the same code authenticated via `signIn`. Read the endpoint's answer before claiming account takeover; the rejection is the control, and it caps the replayable-token impact at session issuance. Verify the account is unchanged by re-logging with the original password.
- **Check the call sites of a redirect helper before calling its edge case a vulnerability.** `safeRedirect` normalized `/login/../..//evil` to a `//`-leading string, but every caller prefixed `window.location.origin`, keeping it same-origin. A bypass in the return value is latent, not exploitable, until a caller consumes it unanchored — label it `info`, not an open redirect.
- **A `200` with an error body is a denial, not an access.** An API can return HTTP 200 with `{"error":"Not authenticated"}` for every rejected call. Read the body, not just the status: checking status alone reads the control as an open endpoint (false positive), and checking status alone on the success path can hide a `{"ok":false}` failure. Verify the body field on both the positive and the negative control.
- **A malformed body can prove a BOLA control without a write.** Sending an update endpoint an intentionally invalid body surfaced the ORM `where` clause; it showed the target id came from the session while the body `id` was ignored — positive proof the object-level control exists, achieved with zero mutations. Use a rejected request to inspect the query plan; never write to a foreign record to test it.
- **Match the query tenant to the token tenant.** A read endpoint that accepts both a Bearer (carrying a tenant) and a `tenantId` query parameter must be tested with the token's tenant and a mismatched query tenant; a `401`/empty on mismatch proves the parameter cannot pivot, a `200` with foreign data proves it can. Do not assume the parameter is cosmetic.

## Supply chain

- **A platform flaw upstream is a flaw in the target.** Map the target's dependencies (e-commerce, payments, hosting, SaaS) and check each against advisories.
- **Headless and PWA storefronts depend on GraphQL**, so mitigations that disable GraphQL are often unavailable — raising exposure to template/GraphQL flaws.
- **Inventory the target's own REST namespaces for agent/tool-execution surfaces.** A WordPress `mcp` adapter registers `POST/GET/DELETE` routes that invoke tools, not just read content; enumerate them separately and verify auth (a `401` is the control, an open route is critical).

## Reporting

- **The management report never exposes exploitation detail.** Business language, business impact, and a clear ask.
- **One finding, one ID, one severity, across both reports.** Divergence between artifacts destroys trust.
- **A zero-day gets an explanation and a badge.** Most readers do not know the term; define it and make it impossible to miss.
- **Every count in the summary must match the finding register.** A stale number is a credibility leak.
- **A read-only report must never read like a test.** When the engagement is passive, the report states the method (GET/HEAD/OPTIONS), the integrity log (0 data altered, no accounts, no credentials) and what only an authorized test could confirm. A reader must not infer that any vulnerability was exploited.
- **An unclassified inference still belongs in the count.** When one finding carries no severity (e.g. an unknown version), state it explicitly in the executive summary next to the severity breakdown so the summary and the register reconcile exactly — never fold it silently into a severity band.
- **An artifact's integrity statement must track the authorization it was written under.** If a later phase authorizes an action that earlier text described as prohibited, update the header, the scope table, and the integrity section together. A stale "not authorized" line contradicts the new evidence and fails the fabrication-free criterion even when no rule was actually broken.
- **A positive result is a finding — continue the sequence and give it a locator.** When an authorized test cannot be exercised because the feature does not exist (e.g. no public signup route), record it as a positive finding with the same ID discipline, evidence locator, and remediation slot ("none — control confirmed") as any other finding, so the register is complete and the executive count reconciles.
- **A passive baseline's risk gauge must not borrow the severity of an inferred impact.** When the highest confirmed severity is a single medium exposure and nothing was exploited, the executive gauge belongs in the low–moderate band, however alarming the inferred impact reads. State the pending-authorization limit in the executive summary and the integrity section together — a report written under a verbal-only mandate that hides that limit reads as a test that never happened.

## Vulnerability analysis (desk-only, Phase 3)

- **A banner that equals the fixed version is not vulnerable.** `nginx/1.30.2` is the release that closes CVE-2026-9256; reading the banner as "old nginx" would have inverted the finding. Check the fix version before the affected ceiling, every time.
- **An unknown version is a limitation, not a vulnerability.** For SAP Commerce, Strapi, FortiOS, NetScaler, Tomcat and SoftExpert the banner gave only the product. Record the exposure, name the candidate advisories, and name the authenticated read that would confirm — never convert "unknown" into "critical".
- **Patch status is not recovery status.** CVE-2025-68686 abuses a symlink a prior compromise left on the appliance; the fix removes the symlink but does not un-read the configuration. Any exposure history forces secret rotation, not just an upgrade.
- **CISA KEV and the vendor's exploitation field can disagree — the KEV date wins.** A vendor advisory marked `Known Exploited: No` still sat on KEV with a federal due date; cite KEV for exploitation status and the vendor for version scope.
- **A remote gateway's login page reveals vendor defaults, not client defects.** A CSP on a FortiGate portal that lists `localhost:14186` and `'unsafe-inline'` is the vendor's template — report it as an observation, not as the client's misconfiguration.
- **Read the raw header value, not only its presence.** An observed `Cache-Control` whose value embeds its own header name is a malformed directive that caches may ignore — a real, evidence-only finding that a "header present" check would miss.
- **Session-cookie flags are visible in the first response.** A `JSESSIONID` with `HttpOnly` but no `Secure` (and no `SameSite`) is a hygiene finding on its own; capture the `Set-Cookie` before the session is established.

## Cloud object storage and data exposure (Phase 3)

- **A cloud container that returns an error without the version header is not necessarily private.** Azure Blob defaults to API version `2009-09-19`; a public container then answers `409 FeatureVersionMismatch` instead of listing. Send `x-ms-version` before concluding "private" — the missing header produces a false negative on the most important check.
- **A public storage listing proves the inventory, not a breach.** Rate on what the names and (minimally) the content show: a production/CMS namespace with contracts is `médio`, and only an observed secret or personal data makes it `alto`. Never download documents to "confirm" — one object request proves anonymous read.
- **Client data under a third-party cloud is still the client's asset.** A storage account referenced from an in-scope app is read-only in scope (as with a GCS bucket); only the cloud provider's own systems are OSINT-only. Say which one you tested.
- **Dangling CNAMEs to cloud-generated hostnames are not reclaimable.** `*.cloudfront.net` and `*.elb.amazonaws.com` names are assigned by the provider and cannot be re-registered by an attacker — record them as DNS hygiene, not as a takeover, and do not spend a phase probing the provider's edge.
- **A confirmed past breach of the same business unit is context, not inflation.** When OSINT surfaces an incident at the same subsidiary that owns a newly found exposure, cite it as threat context and raise priority — but never access the leaked data or restate it as this engagement's impact.
- **A new phase makes the previous management report stale.** If a management artifact already exists, reconcile its counts, severity bands and register with the technical report (or dispatch the manager) before self-review — otherwise the fabrication-free criterion drops on a mere count divergence.

## Active validation (Phase 4)

- **`Server: CPWS` is Check Point, not FortiGate.** A prior watchlist entry mapped `CPWS` to FortiGate and a whole phase was planned around that error. The header is Check Point Web Server; the definitive signal is the response body ("Check Point Mobile" label, "Check Point Software Technologies Ltd." copyright) plus the `/sslvpn/Login/Login` path. FortiGate SSL-VPN serves `/remote/login`. When a `Server` value is ambiguous, read the body before naming the product — a header alone is a guess.
- **An EOL version inside a CVE's affected range is not a confirmed vulnerability.** Confirming that a host runs a version within a CVE's range proves the *exposure* and the *range*, not that the CVE is exploitable there. Rate it `médio` (EOL software + version disclosure) and state explicitly that exploitability was not tested — do not jump to `crítico` on the CVE score alone. "Verified affected range" and "exploited impact" are two different proofs.
- **The default Tomcat 404 page is a version oracle.** `Server: Apache-Coyote/1.1` is versionless, but a forced 404 returns `<h3>Apache Tomcat/X.Y.Z</h3>`. One read-only request to a non-existent path reveals an exact (often EOL) version the banner hid. The same request also distinguishes a protected console (`/manager/html` → `401`) from an exposed one, and `/examples/` → `200` proves a sample app is deployed.
- **A login page leaks the product version where the `/version` endpoint refuses.** SoftExpert's `<title>SoftExpert Suite X.Y</title>` and its `/se/vNNNNN/` asset build path identify the version while `GET /softexpert/version` returns `403`. Check the title and asset URLs before concluding a version is "not exposed".
- **WordPress core version is visible in the login page's own asset URLs.** `GET /wp-login.php` stylesheets carry `?ver=X.Y.Z` for core and `meta generator` names bundled plugins — enough to resolve the version without WPScan, even when the homepage hides it.
- **A CORS reflection must be read verbatim from the captured response.** The reflected `Access-Control-Allow-Origin` value is the evidence; rewriting it as a placeholder (or a different test origin) in the report is fabrication. Record the exact reflected origin and the `Access-Control-Allow-Credentials` value, then scope the impact by the auth model (bearer-token apps downgrade a reflected-origin CORS finding — no cookie-authenticated endpoint means the cross-origin read is not demonstrated).

## Public-surface enumeration (read-only)

- **An admin-looking `/manager/` path can be the customer login of a legacy platform, not a backoffice.** Read the login form before naming the app: `<form id="loginCliente">` with hidden `tipoUser=CLIENTE` and labels "Email ou CPF"/"Senha" is a *customer* login. The module name (`manager`, `Painel`) describes the platform's internal controller, not the user role. The finding is that the legacy platform is still exposed — not that customers can reach an admin.
- **A current storefront on one host does not mean the old one is gone.** A brand can run a new stack (`www`, VTEX/Next.js, `vtex_session_id`) and still expose the previous platform on `api`/`erp` (`JSESSIONID`, `*_Loja.html`, `/manager/*`, `/api/public/*` returning JSON). Map the cookie and the route family per host to decide whether two names are one environment or two; never infer "same environment" from a shared parent domain.

- **A hardcoded credential pair can ship inside a client-rendered login form's initial state.** The HTML form markup shows only field names; the default values live in the component's inline `state` object (e.g. `email: '…', senha: '…'`) and are bound into the inputs via the template. Read the inline state, not just the `<form>`. Rate the exposure (confirmed) separately from the credential's validity (inferred — one authorized login confirms it).
- **A hidden signup link is not a disabled signup route.** A login page can pass a feature flag (`registerNewUser:false`) that hides the "create account" link while the route still returns a `200` registration form. Probe the route directly; the rendered link is not the access control.
- **An SPA catch-all makes per-path status useless for route discovery.** Every path returns the same shell with `200`, including `/cadastro`, `/register`, and `/robots.txt`. Read route existence from the JS bundle (router state tree, redirect allowlist, component names), and confirm the shell by comparing body hashes — a `200` on a path proves nothing on its own.
- **A registration route on one app does not mean the whole portfolio has registration.** In a multi-app surface, the public signup existed only on one product's app; the SSO app and the admin app had none (accounts were admin-provisioned and email-activated). Map the whole portfolio and state the result per app — a single-app check leaves the conclusion unproven.
- **The registration route and the SSO handoff are different surfaces that can coexist.** A `/sso` entry point that exchanges a one-time ticket is for existing, provisioned users; it is not a registration path. Do not infer self-registration from the presence of an SSO endpoint.
- **Serving a post-login app shell without authentication is a client-code disclosure, not a data breach.** A client-side app is meant to be downloaded; the boundary is the API. Report the shell/endpoint-inventory exposure at low severity and verify the API returns `401` before rating it higher.
- **A default credential in public client code is a public artifact, not an exfiltrated secret.** It is shipped to every browser and is the finding itself. Record its location and enough to remediate; mask the value in the narrative and keep the raw public page as the evidence locator, then recommend rotation — the rubric's "no secrets in artifacts" still governs the report text.
- **Client apps of a Brazilian government/education platform often use CPF as the login identifier, and a well-known example CPF can be left as a default.** Recognize the canonical test CPF pattern and check whether it is a real account before rating validity; the presence is confirmed, the account's existence is not.
- **An "anti-enumeration" comment does not prove the response is uniform.** A fixed generic message is non-enumerating only if the client renders the same text for every outcome. A sibling admin flow branched on response fields (`usuarioAtivo`, `emailsMascarados`) and rendered a distinct message for active accounts — a CPF/account-enumeration oracle hiding behind the same feature name. Read the client's branch, not the comment.
- **An impersonation / "view as user" feature's read-only guarantee lives on the server.** When the client says it disables writes only as a courtesy ("the server rejects every mutation"), the test is a direct write request with the impersonation bearer, bypassing the UI. A `200` means the "read-only" session writes as the target — a high finding; a `403` confirms the control.
- **A client-rendered shell served without auth hands over the entire internal API and the role matrix.** Do not dismiss the shell as "just a frontend": its `api()` wrapper and menu gates enumerate the authenticated surface, methods, bodies, and per-role gating. Rate it as a client-code disclosure (low) and use it to plan the authenticated test — the API stays the boundary. A default credential in that same public artifact raises the disclosure's impact from "inventory" to "access path if valid".
- **A client subdomain that presents a certificate for an unrelated company is misrouted, not merely legacy.** A CNAME to an agency/shared host serving `CN=<other-company>` (e.g. a `.com` of a different firm) means the record points at a host that serves another tenant's site. Read the presented issuer/subject with `curl -k -D -` (or `openssl`); the wrong CN is the diagnostic. Rate it on evidence (misrouting + wrong cert) and name the ownership-confirmation step — do not assume the app is the client's because the name is.
- **A private RFC1918 address or an `internal-*.elb.amazonaws.com` CNAME answered by a public DNS record is an infrastructure disclosure on its own.** It publishes internal addressing and the internal load-balancer name; a reachability timeout is not required to report it. Confirm with `dig` twice before rating.
- **A read-only HTTP observation is not an active test, but it must be declared.** A single `GET`/`HEAD` plus a TLS handshake per host, under a passive mandate, states its method and the one-request budget; it proves what the service serves, never that a vulnerability is exploitable. Keep the "confirmed version in a CVE range" and "exploited" claims strictly apart.
- **A CDN can pass the origin's `Server` header while stamping its own.** An edge that adds `x-<cdn>-*` and a `Server: <cdn> webserver` string on its own redirects may still forward the origin's `server: nginx/1.27.3`. Read which hop produced the header before attributing the version to the origin; the value is real, the owner needs care.
- **A deprecated TLS protocol is confirmed by the session, not the request.** `SSL-Session: Protocol: TLSv1` with no `alert protocol version` proves the edge accepted TLS 1.0/1.1. Modern browsers no longer negotiate them, so rate it `baixo` (hardening/PCI), never `alto` on the protocol alone. A CDN edge's TLS policy is the client's domain configuration, not a vendor system to test — one handshake against the client's own name is in scope; do not probe the CDN's other tenants.
- **`server_tokens on` leaks the nginx version on an application error page.** A `502` for `/xmlrpc.php` printed `nginx/1.27.3`, proving the same origin serves the ERP host and the WordPress blog. Reading only the root banner would have missed that the exposed version belongs to one shared origin.
- **A verbal authorization must be recorded exactly as given.** Base = operator declaration; nominal authorizer = not provided; contract reference = not provided. Do not invent a name, document, window or contact to make the record look complete — state the gap and keep authenticated/intrusive work gated behind written authorization.
- **An SPA catch-all makes `/security.txt` and `/sitemap.xml` return `200`.** The body is the storefront shell (~1 MB `text/html`); only `/.well-known/security.txt` (`404`) was a real response. Diff the body against the homepage before calling a file "present".
- **A new phase makes the management report stale — reconcile it in the same run.** Adding TD-13/TD-14 to the technical report forced matching counts, IDs and severities in the management artifact. A mere count divergence between the two reports fails the fabrication-free criterion even when every rule was respected.
- **A white-label/platform residue is strongest when it is served live, not only archived.** A login template carrying another brand's `dominioWeb` in an old capture is history; the same residue in a static asset still returning `200` from the client's host today is a live exposure. Fetch the referenced asset (`/<app>/styles/<brand>.css`) and grep it for the other brand and the platform vendor — a class named `.plataforma-<vendor>-logo` and a `cdn-<brand>.<vendor>.com` URL confirm both the shared platform and the tenant mix in one read. Rate it `baixo` (identity/tenant-governance) unless cross-tenant data is observed, and label hosting/infra that is not observable as inferred.

## Host expansion and light port scan (Phase 4)

- **A wildcard certificate hides the surface from CT — only a wordlist finds the rest.** A client name that never had an individual certificate is invisible to `crt.sh`/Cert Spotter. A service/infra wordlist plus permutations of the known hosts surfaced a monitoring stack, a CI host and a container registry that CT had never shown across three prior phases. Run the wordlist; treat CT as the floor.
- **A resolver timeout is not `NXDOMAIN`.** A first pass labelled most candidates "unresolved" because `dig` returned `connection timed out; no servers could be reached` under load. Parse the answer's `status:` field, re-query failures on a second resolver, and only then count a name as absent — otherwise the inventory is an artifact of the resolver's mood.
- **A `CPE`-based NVD query returns every CVE whose configuration matches that CPE — read each range.** `cpe:2.3:a:grafana:grafana:9.5.1` returned 25 CVEs, but a match is not a fresh attribution: verify the version against the advisory range (`CVE-2023-3128` is `<9.5.4`, so 9.5.1 is in range; `CVE-2025-4123`'s NVD config was broad and its vendor advisory did not list 9.x).
- **Rate an exposed Grafana on exposure + version, not on the worst CVE in the list.** An internet-reachable `Grafana 9.5.1` (EOL) with anonymous access disabled is `médio`: confirmed exposure and EOL version, no confirmed exploitation condition. A CVSS 9.4 in range (`CVE-2023-3128`) that needs Azure AD OAuth — unobservable from outside — does not make it `alto`; state the condition and the untested status.
- **A light port scan belongs on the client's dedicated IPs, not the shared CDN edge.** Port-scanning a name that resolves to a third-party edge tests the vendor and can touch other tenants. Restrict the scan to IPs the client owns (datacenter ranges, cloud project IPs), state which hosts were excluded and why, and treat an all-`closed` row as "host up, nothing listening on the scanned list", not "host down".
- **A `TRACE` method in an `Allow` header is a one-read hygiene finding.** `OPTIONS` returning `Allow: OPTIONS, TRACE, GET, HEAD, POST` is worth an `info` line; do not upgrade it on the method name alone.

## Expanding from prior findings (Phase 5)

- **Audit the finding list before reporting it — the CPE list over-includes.** Re-running the range filter on the same 25 CVEs showed only **19** actually include `9.5.1`; `CVE-2026-27876` (SQL Expressions + Enterprise RCE, 9.1) is ≥11.6.0, and `CVE-2025-4123`, `CVE-2026-42127`, `CVE-2026-27880`, `CVE-2026-14199` and `CVE-2026-21727` are all ≥10/11. The earlier Phase 4 note blamed a "broad config" for one of them; the real cause is the CPE matcher, not a config — filter every entry with `version <= target < lessThan` and never attribute the whole CPE list. Correcting this is a `Range`-criterion improvement, not a downgrade of a real finding.
- **The edition matters as much as the version.** `grafana_build_info{edition="enterprise"}` on `/metrics` upgraded the product identity from "Grafana" to "Grafana **Enterprise**", which brings edition-only CVEs (`CVE-2023-4399`, Enterprise Request-security deny list) into scope. Always read the build-info metric — `/api/health` gives the version but not the edition.
- **`/metrics` deserves its own check and its own finding.** The version endpoint (`/api/health`) and the metrics endpoint (`/metrics`) are separate exposures. Here `/api/health` and `/metrics` were both open, while every data API returned `401`; `/metrics` added the edition, the internal API handler inventory, feature toggles and alerting/DB metrics. Rate it `baixo` (operational metadata, no PII) and keep it distinct from the exposed-version finding so remediation is explicit.
- **A Next.js `_buildManifest.js` is public by design — the finding is the exposed environment, not the manifest.** The 84-route manifest proved the beta was a full storefront (including `/area-vendedor` and `/checkout/*`) but shipping it is normal for Next.js. Report the environment exposure; cite the manifest as evidence of scope, not as a vulnerability.
- **Targeted endpoint checks are not directory fuzzing.** Reading a known list of endpoints (`/api/health`, `/metrics`, `/signup`, `/api/config`) is observation; enumerating an unknown path space is fuzzing and was out of scope. State the distinction in the method so the RoE boundary is explicit.
- **A probe of a host behind a shared CDN edge should re-verify current state, not trust the prior phase.** Re-probing the Phase 4 hosts confirmed the same public exposures and no new service, and confirmed the private-IP hosts remain unreachable — no re-test of the edge, no third-party probe.
- **Automated HTML edits need a structural re-check, not just a visual open.** After editing counts and cards in two large standalone reports, a tag-balance parser confirmed both files were well-formed; a stale count left in one report would have failed the fabrication-free criterion across artifacts.
- **Confirming a hypothesis can *lower* a severity — say so explicitly.** An authorized login attempt refuted a months-old "default credential is valid" inference (the password returned `401`), yet the same credential's identifier proved to be a **real active account** through a sibling enumeration oracle. The honest result is "access refuted, exposure of a real identity remains" — recommend the downgrade with the evidence, never keep the higher severity because it was already printed.
- **"Not single-use" is a test result, not an assumption.** An auto-login token that authenticated on the first exchange authenticated again on the third from a clean cookie jar — the reused-credential class is a real finding, but only if you re-exchange and control the client state (a shared cookie jar produces a false "session issued" on the negative control too).
- **One authorized account cannot prove horizontal BOLA.** Cross-tenant/IDOR needs a second known identifier from another scope; with a single account, rotating route names or guessing IDs yields `404`s that prove nothing. State the limitation and name the test that would confirm it instead of implying isolation is broken.
- **The object-trust differential is a hypothesis; a controlled write to a second account you own is the proof.** The mismatched-id ORM error proved the target id came from the body, but "médio / inferred" was the correct rating until an authorized second test account existed. When the operator grants it, confirm with a benign field write, verify **through the victim account's own session**, then restore — the read-back from the victim's session is the evidence, and the restore is what keeps the finding inside a non-destructive mandate.
- **A write-IDOR's severity depends on whether the victim identifier is reachable.** The same endpoint went from "conditional on a userId leak" to `alto` once the app itself handed over other members' `userId` (a comments feed) and the tenant id was public — the missing piece was not a secret. When rating a BOLA write, check whether the object id is exposed elsewhere in the same app before calling it conditional.
- **Record where a leaked credential actually sits before rating it.** A signup API that returns its own login link puts the token in a response body (server access logs, proxy logs, browser history) rather than in an email — that changes who can replay it and elevates the "no email verification" observation into a token-exposure finding with its own remediation.

## Shell and tooling

- **In zsh, `path` is a special array tied to `$PATH`.** `local path="$1"` inside a function overwrites the command search path, and every later external command (`curl`, `date`, `head`, `sleep`) fails with `command not found` while the function's own line numbers are reported. Never use `path` (or `PATH` in lowercase contexts) as a parameter or loop variable; rename to `endpointPath`, `targetPath`, etc. The symptom looks like a broken environment but is a name collision.
- **Quote `--data` values through an explicit `if`, not `${x:+--data "$x"}`.** Word-splitting turns a JSON body into separate curl options (`option --data {...}: is unknown`). Build the argument list inside an `if [ -n "$body" ]` branch with `--data "$body"`.

## Scoping and authorization

- **When the authorization grants exactly one test account, do not spend a second.** Probe provisioning paths with the **existing** identity: a duplicate e-mail keeps the request from creating anything, and an invalid token cannot mutate state. If a path can only be confirmed by creating an account, mark it inferred and name the test — the one-account budget is a scope boundary, not a suggestion.
- **A phase that finds no vulnerability still produces findings.** Register the controls you confirmed (auth required, tokens validated, provider gated, anti-enumeration) as `info` findings with evidence locators on the same ID discipline as any defect, so the register and the executive counts reconcile. "Nothing exploitable" is a result, not a gap.
- **An expanded authorization can add domains that share only a brand, not infrastructure.** When a client authorizes sibling domains, diff the stack per domain (web server, CMS, hosting, mail, tenant) before assuming a shared application or tenant. Brand siblings frequently run entirely separate systems — one a Next.js/SaaS app, another a WordPress on shared hosting — so controls and findings do **not** transfer between them, and the diff is itself a deliverable.
- **Verify each newly-authorized domain's registrant, not just the brand.** A domain the authorizer names can be registered to a **different natural person** than the authorizer (RDAP). Record the mismatch as a governance caveat and keep read-only discipline until the authority is confirmed — do not treat the authorizer's declaration as proof of registrant identity, and do not infer ownership from a matching brand or a shared admin contact.
- **A client tenant on a vendor SaaS is not the vendor's platform — and the line is per action.** When the client's portal CNAMEs to a vendor (`<tenant>.<vendor>.tld`), a read-only `GET` via the client's subdomain observes the client's tenant and is in scope; creating an account or submitting credentials there writes to the vendor's shared platform and needs the vendor's own authorization. Apply the test per action: if the action cannot be bounded to the client's tenant, skip it and list it. Never let "the client authorized their portal" become "test the vendor's platform."
- **A no-signup portal is a positive finding, not a dead end.** When the authorized "use a normal account" test is conditional on a public signup and the portal has none (`/users/sign_up` → 404), register the absence as an `info` control with its evidence, state the limitation, and name the test that would confirm access control (a provisioned account). Do not invent an account or submit credentials to exercise the test.
- **An update endpoint that keys off the body `id` is a BOLA even when you cannot yet name a victim.** If a member's own `id` updates and a non-existent id yields an ORM "record not found" for the `update`, the client-supplied id is the target — the session is not authorizing the object. You do not need a real victim id to report the mechanism; mark the cross-user impact **inferred**, name the two-request differential as the evidence, and state the confirming test (a second provisioned user id). Do not inflate it to a confirmed write, and do not perform a real cross-user write to "prove" it.
- **When several endpoints expose other users' fields, rate on the field, not the endpoint.** A comments/feed API returning author full names and photo paths to any authenticated member is a privacy/exposure finding (low), even though the feature is "social" — measure the minimum (count, field names, masked values) and never copy the list into the deliverable.
- **A family of endpoints found in one chunk set is an inventory finding, not a vulnerability.** Reading the post-login bundles surfaced ~22 authenticated routes where an earlier phase documented 8. Report the expanded authenticated API map as `info` (it is public client code) and use it to plan the authorization tests — the value is coverage, not a defect.
- **An unauthenticated `200` for `/.env` or `/backup.zip` on an SPA is the shell, not the file.** A `try_files … /index.html` nginx or a Vercel catch-all returns the app HTML with `200` for every path; check `content-type` and body size against the homepage, and treat a `403` on a well-known directory (`/assets/`) as proof that autoindex is off. Confirm before rating an "exposed artifact".
- **A `true` from an identifier oracle is not existence until a random valid-format control says `false`.** A reset endpoint returned `usuarioAtivo:true` for an embedded default CPF; the same endpoint returned `true`-like handling that could have been a checksum echo. Sending a **random CPF that passes the checksum** returned `false` (generic mask) while the target returned `true` with a real masked e-mail — that control is what turned a plausible lead into a confirmed, reportable account disclosure.
- **A placeholder password does not mean a placeholder username.** The embedded default credential's password was refuted (401) and easy to dismiss as dummy data; the **CPF was a real, active account's identifier**, exposed by the public admin shell and confirmable by any unauthenticated caller. Split the credential into its parts and test the identifier separately from the secret.
- **A uniform `200` on a tampered signed token is anti-enumeration, not proof of missing validation.** Step 2 of the reset flow returned `200` for an intact, a signature-tampered, and an out-of-range `sessionToken`; reading that as "the signature is ignored" would be a false positive. The uniform answer is the control; only a valid token for a real account (which must not be used) would move the question.
- **A `401`-for-everything API makes per-path status useless for route discovery.** On a Kestrel API with a global fallback authorization policy, unknown and protected paths both answer an empty-bodied `401`; only a non-empty `problem+json`/JSON body marks a mapped route. Read the body, not the status.


- **A server-rendered leaderboard leaks the member list even when the page makes no API call.** A `/ranking` page that returned no `/api/` literal in its HTML still embedded every top-10 member's full name, photo path and points in its RSC flight payload. Reading only the rendered DOM (or only the network tab) would have missed it; grep the `self.__next_f.push` payload for the row element keys. It is the same class as the comments leak and worth its own finding.
- **Measure reach, do not harvest it.** The task was to count reachable members, not collect them. Paginate to a stated cap, count distinct ids/names, cross-check a second source for a union, and store only counts, field names and masked samples. Keep the raw payload (which carries third-party PII) in `/tmp`, outside the versioned workspace — the finding survives on the count and the field map alone.
- **`totalPages` on a feed is not a member total.** A comments endpoint reported `totalPages: 8` for one lesson; that is pages of comments, not distinct members and not a tenant total. Report "at least N (capped at X pages)" and label any extrapolation as an estimate.
- **A read endpoint that takes a `userId` is not automatically a read-IDOR.** `profile-public` used the body `id` in its client call but the ORM error showed `where: {userId: <session>}` — session-scoped, no BOLA. The same differential on its sibling `profile` showed `where: {id: <body>}` — the confirmed write-IDOR. One invalid body per endpoint tells the two apart with no write and no read of third-party data.

## Gamification and point integrity

- **A points/leaderboard feature is a business-logic surface, not a cosmetic one.** Enumerate every point-earning action from the rendered page and the client bundle (action key → label → points), then classify each as once-only, per-event, or client-enforced. The abuse is usually one of four: a **client-side counter** (`localStorage`/cookie guard), a **missing per-object uniqueness** constraint, a **fabricated object id accepted on write**, or a **monotonic counter with no decrement**. Rate the finding on integrity (leaderboard/rewards), not on access.
- **A "once per day" (or once per object) rule implemented in the browser is not a control.** When the client guards with `localStorage`/cookie before calling the credit endpoint, the endpoint is still directly callable — mark the farm **inferred**, name the two-call test, and do **not** trigger extra credits to prove it when the task forbids farming. The client-side guard is itself the evidence that the server may not dedupe.
- **Map point-earning actions to their write endpoints; the advertised list is not the attack surface.** A gamification page lists the rewards, but credits come from specific writes (`lesson/read`, `lesson/comment`, `social/like`, `social/post`, `certificate/verify`, `login`). The farmable ones are those whose object id the client controls and the server does not validate. An action gated by an entitlement the account lacks is not reachable — say so instead of testing it.
